# Deploying Growth OS

Live today: **https://growthos-b0t9.onrender.com** (Render, free plan, deploys automatically from `main`).

## Rules every deployment follows

- `APP_ENV=production` (the default): no demo clients, no mock models, and the app refuses to start with a weak `JWT_SECRET`.
- A **new, empty database**. Never point production at the local `growthos.db` or `demo_mock.db` (they hold fictional demo clients). The schema is created by Alembic migrations at startup.
- **One process, one worker.** The orchestrator, pacing buckets and rate limiter live in the process.
- API keys go in the host's environment settings (Render: the **Environment** tab), never in git.
- Check `https://<url>/healthz` after every deploy. It must show `"env":"production","fixtures":false`. It also says which database is used and whether storage is ephemeral.

## Choose a database

| Option | Cost | What happens to data | Use it for |
|---|---|---|---|
| **A. Free, SQLite in `/tmp`** (`render.free.yaml` as is) | $0 | Wiped on every redeploy, restart **and idle spin-down** (Render free services sleep after 15 minutes without traffic; their filesystem is ephemeral). Every page shows a banner saying so. | a demo link you test in one sitting |
| **B. Free, hosted Postgres** (`render.free.yaml` + `DATABASE_URL`) | $0 | Kept across restarts and spin-downs | the interview link, a pilot |
| **C. Paid instance + disk** (`render.yaml`) | about $7.25 a month | Kept on the disk; back it up | production with real clients |

Option B works because the app runs on Postgres as well as SQLite: migrations, the whole test suite (218 tests) and a production-mode boot were run against PostgreSQL 15 locally. It has **not** been run against a specific hosted provider yet. Free Postgres options include Neon and Supabase (check their current free-plan limits); Render's own free Postgres is deleted after 30 days, so it is not a good fit. Paste the provider's connection string as given (`postgres://user:pass@host/db?sslmode=require`); the app converts it for its driver.

## Render, free plan (A or B)

1. Render dashboard → **New → Blueprint** → pick the repo and the file `render.free.yaml` (or, for an existing service like the live one, set the same variables by hand in **Environment**).
2. In **Environment**, set at least `GROQ_API_KEY`, `TAVILY_API_KEY` and `GOOGLE_API_KEY` (Gemini is the judge and the extraction model; free key at aistudio.google.com). `JWT_SECRET` is generated by the blueprint; set a long random value by hand otherwise.
3. For option B, replace `DATABASE_URL` with the hosted Postgres URL.
4. After the first deploy, set `APP_BASE_URL` to the `https://…onrender.com` URL and redeploy (OAuth redirects and secure cookies need it).
5. Optional: `HUNTER_API_KEY` (lead emails), `ADMIN_EMAIL` + `ADMIN_PASSWORD` (a platform admin for the data view and account managers), `SIGNUP_INVITE_CODE` (gate signup on a public link), Gmail variables (below).
6. Check `/healthz`. With option A you should see `"ephemeral_storage":true`; with B, `"database":"postgresql","ephemeral_storage":false`.

Free-plan behaviour to expect: the first request after 15 idle minutes takes about a minute (the service wakes up). With option A that wake-up starts from an empty database, so sign up again. A run in progress survives only while the service is awake; the Activity page keeps it awake while you watch it.

**Pushing to `main` redeploys the live site.** With option A that also wipes its data. Work on a branch and merge when tests pass.

## Paid instance with a disk (C)

`render.yaml`: instance type `starter`, a 1 GB disk at `/data`, `DATABASE_URL=sqlite+aiosqlite:////data/growthos.db`. Back up the disk; losing it loses accounts, drafts and Gmail connections.

## Any Docker host

```bash
docker build -t growth-os .
docker run -p 8000:8000 -v growthos-data:/data --env-file .env.production growth-os
```
`.env.production` holds the variables from `.env.example` (never `LLM_MODE=mock`). Not verified here: Docker is not installed on the machine this was built on. What was verified instead: a clean Python 3.13 environment installed `requirements.txt`, ran the image's start command on a copy of the repo filtered by `.dockerignore` (so no `.env` and no `.db` files), migrated an empty database and answered `/healthz` with `"env":"production","fixtures":false`. Render built and ran the same Dockerfile for the live site.

## Gmail sending

1. Google Cloud Console → APIs & Services: enable the Gmail API, configure the OAuth consent screen, create an OAuth client of type **Web application**.
2. Authorized redirect URI: `<APP_BASE_URL>/auth/gmail/callback` (`/oauth/google/callback` is served too). It must match `GOOGLE_REDIRECT_URI` exactly.
3. Set `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` and `GOOGLE_REDIRECT_URI`. Scope is `gmail.send` only: the app can send mail the founder approved and cannot read the mailbox.
4. While the OAuth app is in **testing** mode, only the test users listed in Google Cloud can connect, and mail goes only where Google allows. To show sending end to end, use **Leads → Add a lead manually** with your own address, approve the drafted email, then send.
5. `ENCRYPTION_KEY` (any long random value, or a Fernet key) encrypts stored Gmail tokens. Without it they are derived from `JWT_SECRET`, so changing that secret disconnects Gmail and founders reconnect.

## Smoke test after a deploy

`/healthz` → sign up → onboarding → every tab shows an empty state → start research. If a key is missing, the run stops at that step and the Activity page says which key and how to fix it. Research and strategy take about 1 to 1.5 minutes on the free tiers; posts about 3 minutes; leads about a minute.
